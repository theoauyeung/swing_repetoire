# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Research project on MLB swing shapes using Statcast bat tracking (2024+). Two questions:

1. Swing-shape value (Facet 1): a per-batter GMM clusters a hitter's swing shapes, and a custom xRV model grades each shape's run value conditioned on the pitch (location, type, platoon) but not the count or game state, so Swing+ measures what a swing shape is worth on a given pitch while staying count-neutral (count variation is reserved for the adjustability value analysis).
2. Repertoire diversity (Facet 2): batter-level scalars (repertoire size, usage entropy, repertoire expansiveness, context-responsiveness) test whether a wider, more adjustable repertoire improves outcomes.

`docs/research-design.md` is the source of truth for methodology, confirmed design decisions, limitations, and milestones. Read it before touching modeling code. The decisions there are settled: strictly per-batter GMM, custom xRV, and a shape defined as 5 mechanics features that exclude intercept location. `docs/worklog.md` tracks what's actually been built.

### Repertoire+

`repertoire.py` → `data/repertoire_scores.parquet`. A purely descriptive, count-aware measure of repertoire width: `expansiveness = mean_pairwise_dist × √effective_shapes`, where `mean_pairwise_dist` is the usage-weighted mean pairwise Euclidean distance between a unit's cluster centroids (each of the 5 shape features standardized by cohort (league) swing-level SD for cross-hitter comparability) and `effective_shapes = 1/Σweight²` (inverse-Simpson, the usage-effective shape count).

Design history: mean pairwise distance alone is count-blind (average dissimilarity of two random swings), so it ranked 2-extreme-shape hitters above 6-moderate-shape ones (corr with `k` ≈ −0.12). Multiplying by `effective_shapes` (eff¹) overcorrected — count then drove 84% of the ranking (corr with `k` ≈ +0.82). The `√` on the count term (eff^0.5) balances them: spread and count each contribute ~half the ranking variance (corr with `k` ≈ +0.59; corr with spread ≈ corr with eff ≈ 0.66), so a wide 2-shape repertoire can still out-rank a mediocre 5-shape one. Chosen over MST-length (pure geometry, drops usage) and Rao's Q (count reward saturates).

Geometry only: no run value, quality, or adjustability; all 5 features equal-weighted (incl. `bat_speed`); k=1 → 0 floor. Use `repertoire_pctile` as the headline, not `repertoire_plus`: 24% of units are single-shape and pile up at the 0 floor, which skews the "50 = average" reference. `repertoire_plus` is on the same scale as Swing+: `50 + 10·z` clipped to [0, 100]. Diagnostic columns `mean_pairwise_dist` and `effective_shapes` are retained in `repertoire_scores.parquet`. It reuses cluster_summary's raw centroids directly, since the horz_attack_angle pull-mirror is distance-invariant.

Pegged to a frozen 2024-25 baseline (2026-07-16): the feature SDs, the `50+10·z` mean/SD, and the percentile grid are computed once from the 2024-25 cohort and persisted to `src/uncommited/repertoire_reference.json` (local-only, not in the repo — a fresh clone re-pegs on first run), then reused on every later run so repertoire_plus/pctile stay comparable as seasons are added (like OPS+/wRC+). Delete that JSON to re-peg. Caveat: `cluster_summary` centroids are still pooled across all clustered seasons, so a true per-season cross-season plot also needs per-season centroids (unbuilt) — the peg removes scale drift, not centroid pooling.

### Adjustability

`adjustability.py` → `data/adjustability.parquet`, v4 single-regression (2026-07-22); renamed from `context_response.py`, a stale v1 label — headline column has always been `adjustability`. Measures how much a hitter's swing depends on the situation, distinct from Repertoire+ width (a hitter can be wide-but-random or narrow-but-adjustable). Measured directly on the volitional trait dials (`bat_speed`, `swing_length`, `swing_path_tilt`) — not on shape clusters (v1 measured MI over clusters, a substrate artifact) and no longer v2's single signed count slope. Per (batter, stand), 2024-25, ≥400 swings (471 units). Unsigned magnitude.

Method (v4): one joint regression per hitter per dial, `dial ~ location surface (px, pz, squares, interaction) + situation dummies`. The headline `adjustability` = the incremental adjusted R² the whole situation (count+gamestate+pitch) adds over a location-only baseline, averaged over the 3 dials, floored at 0. Each per-axis column is that axis's unique contribution — variance it adds net of location and the other two axes — so `adj_count` holds pitch type fixed. This replaced the v3 two-stage build (global location residualization, then a separate per-hitter situation R²): one model, and each hitter's own location relationship is fit rather than a single league-average surface.

Why v4 is better: v3's global surface let pitch-movement-correlated-with-location leak into `adj_pitch`; per-hitter location control removed it (adj_pitch mean 0.058→0.030), so the headline is now count-led (corr with `adj_count` 0.72 > `adj_pitch` 0.57), pointing at the axis that actually pays off. Per-axis means: count 0.021, pitch 0.030, gamestate 0.002. `adj_count` is rank-stable across v3→v4 (r=0.94); `adj_pitch` moved most (r=0.75). YoY reliability (v4, recomputed 2026-07-23): `adjustability` r=0.67, `adj_count` r=0.69, `adj_pitch` r=0.64 — all repeatable; `adj_gamestate` r=0.28 is noise (v3 read 0.75/0.72/0.78/0.19, same conclusion). The v4 recompute lives in `adjustability_results.ipynb`. v2's directional construction is in git history (988a0f1). See research-design.md Part D + docs/adjustability-decontamination.md.

### Adjustability value (replacement benchmark — headline)

`src/adjustability_value.py` → `data/adjustability_value.parquet`. Season-run accounting for situational swing changes. **466 units, 2024-25, ≥400 swings, 553,459 swings** (down from 471/573,198 once the pitch-characteristic join is required).

**Estimand (replacement benchmark, 2026-08-04).** For every competitive swing: `xRV(his actual swing) − xRV(a randomly drawn OTHER hitter's situational policy applied to his same situations and pitch)`, averaged over `N_REPLACEMENTS=10` draws, summed over two seasons and halved to give season runs. **"Replacement" means a randomly drawn hitter from this same 466-unit cohort, NOT WAR's replacement level** — the bar is an average big-league adjuster, not a fringe one. The old "vs. his own de-situated swing" quantity survives as `runs_vs_desituated` for side-by-side display but is NOT the headline. **The benchmark was the whole problem:** vs zero, 96.1% of hitters "gain," `corr(runs, n_swings)=+0.63`, and elite hitters (Nick Kurtz 2nd in RV/swing) rank near the bottom — it was a playing-time stat. Zero is a strawman, because "adjustment vs. no adjustment" can only point one way whenever adjustment tracks the pitch at all. A *pooled* league policy is the opposite failure (only 25% of hitters beat it — it wins by being smoothed, not by being right). A random replacement is precision-matched: the replacement's fitted policy block carries the same estimation noise the hitter's own block does. Result is two-sided by construction, 52.4% positive.

**Policy block.** Per unit, a lstsq map from a mean-CENTERED situation dummy row to a shape displacement in league-SD units. Centering is what makes a block transferable — a replacement's block describes how he *deviates* by situation, not his personal average swing, so applying it to another hitter doesn't import the replacement's mechanics.

**Shape model.** Per-unit OLS: `shape ~ location surface + pitch_group + pitch characteristics + count dummies + gamestate dummies + platoon dummies`. Both arms are CROSS-FITTED (5-fold `KFold(shuffle=True, random_state=7)` within unit); using the same fold's coefficients for both arms is required, since the headline is a difference of fitted values and fold noise cancels only when the folds match.

**Pitch characteristics are controls (`src/uncommited/pitch_controls.py`, 2026-08-04).** Velocity, movement, spin and release from `data/pitch_chars.parquet` (pulled by `src/uncommited/extract_pitch_chars.R` off Baseball Savant; 97.0% join rate) enter every arm via `counterfactual.build_design(extra_controls=...)`. Not optional: raw situational displacement repeats at r=0.616 with location controls alone and **0.394** once the pitch is accounted for. Most of the apparent adjustment was reaction to different stuff. `adj_pitch` collapses hardest.

**Counterfactual construction.** De-situation sets each situation axis's dummy columns to their unit column MEAN rather than to a reference category — mean-preserving, so the hitter's average swing is unchanged and only situational *variation* moves. Axes: `count` (balls, strikes), `gamestate` (base_state, outs_when_up), `platoon` (pitcher_throws).

**`pitch_group` and pitch characteristics are CONTROLS, never de-situated.** Held at observed values in every arm. A hitter cannot choose his swing before identifying the pitch, and the measured shape on a breaking ball partly reflects being fooled — de-situating it removes consequence rather than policy. This is why the decomposed axes are exactly count / gamestate / platoon.

**xRV variant.** `assemble_xrv` (not the neutral variant) — the mechanism under test is whether two-strike compression buys enough contact to pay for the strikeout risk that lives in `rv_whiff`.

**`pitch_type` category cast.** Must be cast to `category` ONCE on the full frame (all 17 league categories) BEFORE per-unit slicing. Otherwise each unit infers its own integer codes and every XGBoost prediction is silently wrong. `python src/adjustability_value.py --verify` scores observed shapes and checks max deviation against the published `xrv_swings.parquet`; it reported max deviation 0.000e+00.

**Output columns.** `runs_total` (season runs vs replacement, all axes), `runs_count`, `runs_gamestate`, `runs_platoon`, `runs_interaction` (the cross-term, computed as `runs_total` minus the three single-axis terms, so it closes the identity by construction), `runs_total_2k` (two-strike swings only), `runs_per_swing`, `runs_vs_desituated` (the retired vs-zero quantity, kept for the benchmark figure), plus the prescriptive layer below. A second output, `data/adjustability_gradients.parquet`, is long at unit × axis × cell × dial.

**Key findings (2026-08-04, replacement benchmark).** `runs_total` mean **+0.140**, sd 1.034, range [−2.796, +5.034], **52.4% positive**. Axis means: count +0.026 (46.8% pos), gamestate −0.002, platoon +0.102, interaction +0.013. `runs_vs_desituated` for contrast: mean +1.561, 96.1% positive. The confounds are gone: `corr(runs_total, n_swings)` +0.626 → **+0.133**, `corr(runs_total, swing_plus)` = **−0.079**. Domain sanity passes — Judge +1.93, Teoscar Hernández +2.19, Arraez −0.72, Schwarber −0.74. `corr(runs_count, adj_count)` = **+0.619** (was +0.298; the vs-zero version was mostly playing time).

**The two-strike sign REVERSED with the benchmark.** Under vs-zero, `runs_total_2k` was −0.028 and the documented claim was "all count value accrues on non-two-strike swings." Under the replacement benchmark it is **+0.122, 60.3% positive — the highest %positive of any axis.** Beating a frozen swing is easiest early in the count, where any adjustment beats none; beating another hitter's policy is only measurable where policies actually differ, which is two strikes. Same swings, opposite conclusion. Do not quote the old "two-strike contribution is zero" line.

**Prescriptive layer 1 — *how much* (α), added 2026-08-04.** Two fixes to the old support-constrained α, which was a grid artifact (86% of units pegged at the α=2.0 ceiling). First, the grid now runs to 8.0, so the value curve's turn is inside it: `alpha_peak_unconstrained` is interior for 454 of 471 units (median 4.0). That column is a curvature diagnostic, explicitly extrapolative, and is NOT a recommendation. Second, the binding constraint is no longer the observed-percentile envelope — that envelope is built from observed shapes, whose execution noise (~1.5 SD) dwarfs the situational displacement (~0.37 SD) being blended, so it almost never rejects. It stays as a hard rail. The recommendation column `alpha_star_policy` is capped instead by a LEAGUE-REFERENCED displacement rule: admit α only if `α · displacement_sd ≤ Q`, where `displacement_sd` is the unit's mean situational displacement in per-feature SD units and `Q` is the cohort 90th percentile (0.445, frozen in `src/uncommited/adjustability_policy_reference.json`; median unit is 0.317). Non-circular by construction — a within-hitter envelope would degenerate to α ≤ 1. Result: 81 units told to modulate less, 107 to hold, 283 to modulate more; `corr(alpha_star_policy, adj_count) = −0.46`, i.e. the cap leaves room for low modulators and none for those already at the top. `runs_at_alpha_star` mean +0.378 season runs (counting stat; use `runs_at_alpha_star_per_swing`). Per-axis columns `alpha_star_{count,gamestate,platoon}` come with `runs_range_*` as a flatness detector — median range is 3.848 on count vs 0.374 gamestate and 0.332 platoon, so the two weak axes' argmaxes are close to noise and must be read beside their range.

**Prescriptive layer 2 — *which lever* (per-dial gradients), added 2026-08-04.** α can only say "more or less of the same": it rescales the direction the hitter already moves in, projecting a 5-dimensional problem onto one line. The gradient layer answers which dial. For each swing, central finite difference of xRV at ±0.1 SD on each of the 5 shape features, rescaled to runs per +1 league SD, probed at OBSERVED shapes so it reads a local slope rather than extrapolating. Written long to `data/adjustability_gradients.parquet` at unit × axis × cell × dial, cells ≥25 swings. Situation cells are coarser than the de-situation axes: count = 0/1/2 strikes, gamestate = base_state, platoon = same/opp-hand. **The prescription is `grad_delta_runs_per_sd`, not `grad_runs_per_sd`** — the raw cell gradient is dominated by the hitter's own baseline, so ranking on it surfaces the largest cell (opp-hand, ~70% of swings) for every hitter; the delta subtracts his all-swing gradient and is what makes the advice situational. Read it beside `shift_sd`, how far his fitted swing already moves that dial there: the prescription is the gap. **Deltas are n-weighted contrasts within an axis and sum to exactly zero across its cells** (verified 0.0000 on all five dials), so they are read per cell and never summed to a season total — `situational_runs_per_quarter_sd` scales a realistic +0.25 SD move over that CELL's own season swings, not the hitter's full season. The unit-level roll-up is per axis (`top_lever_count`, `top_lever_gamestate`, `top_lever_platoon`, each with `_runs`), never a single overall argmax: count carries ~10× the situational gradient of the other two, so one winner read `count` for 466 of 471 units and buried the other axes. Feasibility is out of model — the gradient prices a shape change, it does not know whether the hitter can execute it.

**Validation verdict: Qualified (re-run 2026-08-05 on the replacement benchmark + pitch controls).** Predictive: `rv_per_swing` θ=+0.0887 (p=0.0266, significant); `woba_swing` θ=+0.0544 (p=0.1734, **null**). `rv_per_swing` is the more circular of the two (close to what xRV is trained to reproduce); `woba_swing`, the less circular outcome, still fails — though it moved from p=0.5617 under the old build, so the benchmark swap helped without closing the gap. Convergent: `runs_count` ~ `twostrike_rv_penalty` r=0.054; `runs_count` ~ `adj_count` r=0.619. Split-half `runs_total` r=**0.589** (n=377 units with ≥150 swings in both seasons), up from 0.560 but still below `adjustability`'s YoY bar of 0.67. **Placebo caveat: the shipped placebo (ratio 0.11) scores `runs_vs_desituated`, NOT `runs_total`** — shuffling situation labels within a unit while the replacement blocks come from unshuffled hitters would compare two different worlds, so the test deliberately runs on the self-contained de-situated arm (see the `placebo` docstring). The aim-destroying placebo for the replacement benchmark is `experiments/directional_placebo.py` (ratio 0.012 on the pre-pitch-control build). Read `runs_total` as an accounting decomposition with internal validity, not as a validated predictor of run production.

**Prescriptive layer verdict: SPLIT (re-run 2026-08-05).** The α layer and the gradient layer are gated separately and do not stand or fall together — never collapse them to one label. Each season half is re-estimated independently (separate regressions, separate folds, and separate policy caps; borrowing the pooled cap would give the halves a shared input and inflate r). Full ordering, n=377: `alpha_star_policy` **0.299**, `runs_at_alpha_star_per_swing` 0.299, `alpha_peak_unconstrained` 0.348, `displacement_sd` 0.395, `grad2k_horz_attack_angle_pull` 0.441, `grad2k_swing_length` 0.447, `runs_per_swing` 0.481, `marginal_runs_per_alpha` 0.494, `grad2k_bat_speed` 0.511, `runs_vs_desituated` 0.585, `runs_total` 0.589, `grad2k_swing_path_tilt` 0.595, `grad2k_vert_attack_angle` **0.684**. Pitch controls moved α *down* (0.357 → 0.299) and `displacement_sd` down hard (0.616 → 0.395) — consistent with much of the old apparent modulation having been reaction to pitch mix. `grad2k_vert_attack_angle` is unchanged at 0.684, so the one prescription that matters is also the one the controls did not touch. **`alpha_star_policy` is below the pre-committed 0.5 floor, so *how much* to adjust ships as a cohort-level statement only and the per-batter column must be documented as unreliable.** *Which lever* is stronger but not uniform: 3 of 5 dials clear 0.5, and `grad2k_vert_attack_angle` at 0.684 is the most repeatable quantity in the whole build (above `runs_total`, at `adjustability`'s YoY bar). Prescriptions on the vertical-plane dials carry more weight than those on length or horizontal angle.

**The two designs diverge (2026-08-04).** The first draft and the counterfactual are not two estimates of one quantity — they pose different counterfactuals. The first draft varies the **situation** (2-strike vs 0–1, matched on `pitch_type × zone`) and watches realized `delta_run_exp`; the counterfactual holds the situation fixed and varies the **behaviour** (actual fitted swing vs. de-situated fitted swing on the identical pitch), priced by modeled xRV. Each design's weakness is the other's strength: real outcome / contaminated contrast (the pitcher changes too), versus clean contrast / modeled outcome. They share no ranking: `corr(runs_count, twostrike_rv_penalty) = +0.003`, top-50 overlap 4 of 50 against a chance baseline of 5.3, `corr(runs_per_swing, twostrike_rv_penalty) = +0.050`, `corr(runs_total, adjustability) = +0.100`. They agree only on their shared mechanical input (`corr(runs_count, adj_count) = +0.298`). Both are correctly implemented; the penalty measure credits outcomes reached by any route (pitch recognition, zone discipline) while the counterfactual credits only the swing-shape channel. **On external support the first draft is the stronger of the two** — θ=+0.145 (p=0.0003) on realized run value, against the counterfactual's Qualified verdict. The counterfactual's advantage is conceptual cleanliness, which has not yet been shown to buy predictive power. Do not present either as the single answer; a 2026 holdout is the test that would discriminate. Figure: `results/plots/adjustability/adjustability_value_two_designs.png`.

### Adjustability playbook (the coachable readout)

`src/adjustability_policy.py` → `data/adjustability_prescriptions.parquet` searches, per unit × axis × lever, the signed step (`STEP_GRID` ±0.15 to ±0.75 league SD) that buys the most runs under a mean-preserving ordinal contrast, subject to an envelope rail and a repertoire rail (cell mean within `MAX_CENTROID_SD=1.0` of a demonstrated GMM centroid). `bat_speed` is excluded from `LEVERS` for reverse causality. **One script, two stages** (consolidated 2026-08-06): stage 1 is that search (~25 min, every candidate shape re-scored through xRV), stage 2 turns the steps into instructions and writes `data/adjustability_playbook.parquet` (6,745 rows, unit × axis × lever) + `results/adjustability_playbook.md` in seconds. `--report-only` runs stage 2 against the existing prescriptions parquet, which is what you want whenever the wording or pooling changes but the search does not.

**Three levels, and every row says which one it should be read at.** The `read_at` column is `batter`, `batter (direction only)`, or `type / league`, assigned from `data/adjustability_policy_reliability.parquet` (written by `experiments/policy_search_gate.py`, which re-runs each season end to end — own regressions, own folds, own gradients; cluster centroids stay pooled because that is an upstream stage, like the frozen league scale). Thresholds: step split-half `r ≥ 0.40` → batter; else sign agreement `≥ 0.55` (chance 0.50) → direction only; else type/league. **Reliability annotates, it does not exclude** — all three axes ship. Gate result: count steps repeat at r = 0.413–0.585 with 0.599–0.788 sign agreement; gamestate at −0.032–0.109 and chance sign agreement; platoon at 0.092–0.363, with only `vert_attack_angle` (r=0.363, agree 0.607) clearing the direction bar. *Which* lever wins is identified on every axis (same-lever agreement 0.555–0.578 vs chance 0.25); only the signed size is count-specific.

**Steps ship in the dial's own units, not league SD.** `step_native` + `step_unit` convert `step_sd` through the frozen `shape_sd` in `adjustability_policy_reference.json` (tilt 6.85°, length 0.861 ft, VAA 10.51°, HAA 17.22°), with swing length rendered in inches. The SD scale is kept internally because it is the only one on which four different dials are comparable, but nobody can act on "0.5 SD". In native terms the ±0.15–0.75 SD grid is roughly ±1.0–5.1° of tilt, ±1.6–7.8" of length, ±1.6–7.9° of attack angle, ±2.6–12.9° of aim.

**League policy.** `share_positive` is computed among the hitters the search MOVES, not over all 466 — ~30% sit at the status quo and are abstentions, not votes. Count is near-unanimous: 98.1% of movers flatten `vert_attack_angle` with two strikes (median −5.3°, +2.392 held-out season runs, the biggest line in the build), 90.4% flatten `swing_path_tilt` (−3.4°), 96.2% *lengthen* `swing_length` (+5.2", against compression folklore, but it pays least at +0.407). Gamestate votes are 43–58%, i.e. at chance — that axis has no shared direction at all, so its positive runs (`vert_attack_angle` +0.890) come from different hitters moving different ways. Platoon's one consensus is 70.5% swinging more uphill vs a same-handed arm (median +3.2°, +0.778).

**Hitter types.** Power / Contact = outer quartiles of z(bat speed) − z(contact rate) (95 Power / 98 Contact / 273 Balanced), the same split as the 2026-08-04 gradient work. Compare types on `runs_gain_per_100`, never `mean_runs_gain` — the latter is a season-runs total and ranks playing time. On the count axis Power buys most from flattening (`vert_attack_angle` 0.396 vs Contact 0.262) and Contact most from re-aiming (`horz_attack_angle_pull` 0.180 vs Power 0.103): same direction, different lever priority.

**Caveats.** The step grid caps at ±0.75 SD (±12.9° on the widest dial) and the largest prescriptions sit on that boundary, so they are lower bounds. Sample cards in the markdown are drawn at each type's MEDIAN total gain — ranking on total gain surfaces the highest-volume hitters. `runs_gain` is NaN for units below the swing floor in one season (no held-out price).

### Archetype lexicon

`swing_label.py`. Archetypes are defined on the 4 geometry features only (tilt, length, VAA, HAA_pull). `bat_speed` is a reported descriptor, not a defining axis, because its "state not trait" ICC drags a 5-feature carve into an effort bin. This is a naming overlay only; `cluster.py` still defines shapes with all 5 features. Three archetypes (`K_ARCH=3`): Level Oppo / Level Center / Uppercut Pull. MLB geometry sits on a level-oppo ↔ uppercut-pull diagonal.

`K_ARCH=3` is a deliberate interpretability choice, not the raw BIC minimum: after MERGE_SEP moved 2.0→1.75 (2026-07-13) the finer cluster pool makes BIC marginally prefer K=2 (13188.8 vs 13222.2), and at K=3 the two level components collide in the same naming cell. We keep 3 for the useful middle band and moved the `HAA_OPPO` naming boundary −5.0→−6.5 so they name apart (Level Center at haa_pull ≈−5.6 vs Level Oppo ≈−7.6). `cards.py` (Layer 2) enriches each with a `context_tag` (top-3 over-indexed situations) to produce `archetype_detailed`, so same-archetype shapes read apart. Cluster 0 (the primary swing) is labeled `"Primary"` in `archetype_detailed`, while the true archetype stays in `archetype_name`.

## Architecture and conventions

- `src/uncommited/` is gitignored and holds the local-only files: the data pull (`extract.py`, `features.py`, `extract_pitch_chars.R`), DB access (`db.py`), the shape cards (`cards.py`), validation (`adjustability_value_validate.py`), the presentation helpers (`leaderboard_preprocess.py`, `leaderboard_table.R`, `value_flowchart.py`, `pitch_controls.py`), and the three frozen reference JSONs (`repertoire_reference.json`, `adjustability_reference.json`, `adjustability_policy_reference.json`). Anything importing a module from there (`adjustability_value.py`, the `import db` cell in `adjustability_results.ipynb`) puts that folder on `sys.path` explicitly; scripts inside it resolve the repo root with `parents[2]`. Because the reference JSONs are no longer in the repo, the frozen pegs live only on this machine — a fresh clone re-pegs against whatever cohort it sees, and the scores would not be comparable to these.
- `data/` is gitignored and holds all extracts. Never commit it; it contains athlete data. Parquet is the interchange format between stages, and markdown (`profile.md`, `cluster_catalog.md`) is the human-readable output of each stage.
- `results/plots/` holds rendered notebook outputs as PNGs (committed, unlike `data/`). Both notebooks write there via `PLOTS = ROOT / 'results' / 'plots'`: matplotlib figures via `fig.savefig`, and table/Styler outputs via `dataframe_image.export(obj, str(path), table_conversion='matplotlib')`. Use the `matplotlib` backend, not the default `chrome`/`selenium` (no browser in this env; `matplotlib` renders the gradient heatmap fine and needs no extra binary). Figures aggregate cohort-level results only, so no athlete PII gate is needed.
- Competitive swing (no DB flag exists, so `features.py` defines it): bat-tracked (5 shape features present) + not a bunt + `bat_speed >= 50` + angle artifacts dropped (`|horz_attack_angle| <= 45`, `vert_attack_angle` in [-45, 75]).
- Shape feature vector: `swing_path_tilt`, `swing_length`, `bat_speed`, `vert_attack_angle`, `horz_attack_angle`. Clustering uses `horz_attack_angle_pull` (handedness-mirrored, + = pull) so L/R hitters share a frame. Intercept location coords are deliberately excluded from shape (98–99% pitch-location artifact). `ball_bat_intercept_y` is kept only as a separate timing descriptor, never in the shape vector or as an xRV mediator.
- Clustering unit is `(batter_id, batter_stand)`, not batter alone. A switch hitter's L and R swings are different movements, so each stance clusters (and enters Facet 2) as its own "player": Cal Raleigh L vs Cal Raleigh R. Only `horz_attack_angle` is handedness-mirrored; pooling both stances would make the GMM separate on stance instead of shape. All three outputs carry `batter_stand`. `batter_repertoire` and `cluster_summary` also carry a display `label` that suffixes the stance only for switch hitters ("Cal Raleigh (L)"), leaving one-way hitters bare ("Aaron Judge").
- Clusters are strictly per-unit and not comparable across units. Cluster 0 = that unit's primary (highest-usage) swing. All cross-unit analysis must use unit-level scalars (`batter_repertoire.parquet`), never shared cluster IDs.
- GMM k selection is minimum-BIC (early-stop, no occupancy floors) followed by a post-BIC merge. BIC over-segments at large n into large-but-near-duplicate components, so `cluster.py` merges component pairs closer than `MERGE_SEP=1.75` (within-cluster-SD Mahalanobis) into one shape. Reported `k` is post-merge. This is not an occupancy floor: the phantom components are large (~28% usage), so the problem is separation, not size. Identifiability cap is `k_max = n // 20`. Cohort is ≥150 competitive swings per `(batter, stand)` unit (lowered from pooled-300 to keep switch hitters' weaker side). Post-merge: mean k ≈2.26, median 2, max 6 (MERGE_SEP=1.75; was ≈1.9 at 2.0). 13% of units are single-shape.
- Count-based diversity metrics (`k`, `effective_shapes`) correlate with `n_swings` (r≈0.71) and must be sample-size-controlled before Facet 2.

## xRV status

`src/xRV_model.py` is built and committed. Predictors: 5 shape features + `same_hand`, `plate_x_pull`, `plate_z_norm`, `pitch_type` (no count, no game state — CONTEXT intentionally excludes count). Three XGBoost models (`p_bip`, `p_foul`, `v_bip`); hyperparameters fixed from `experiments/sweep.py` (2024 train / 2025 val); trained on 2024-25, held-out test on 2026. Outputs `data/xrv_swings.parquet` with `xrv`, `xrv_grade` (0-100, 50 = league average, count-inclusive run-value layer), and `xrv_grade_neutral` (count-stripped: same ML models, league-average-weighted run values instead of per-count). Validation: realized_rv vs `delta_run_exp` corr=0.957. `data/re24.csv`, `count_values.csv`, `count_transitions.csv`, `linear_weights.csv` are the run-value tables it reads.

`xrv_grade` vs `xrv_grade_neutral`: the ML models (p_bip, p_foul, v_bip) already have no count in CONTEXT. Count enters only through the run-value layer (`rv_whiff(b,s)` = lw_K − ERV(b,2) at 2 strikes ≈ −0.25–0.45 vs −0.03–0.07 at 0-1 strikes). `xrv_grade_neutral` replaces per-count run values with their empirical frequency-weighted averages (rv_whiff_neutral ≈ −0.119), making grades comparable across counts. Use `xrv_grade` for Swing+ leaderboards; use `xrv_grade_neutral` as a Swing+ control in regressions that also use count-stratified outcomes (e.g. `twostrike_rv_penalty`). Aggregate hitter xRV vs `pitch_values.ipv` calibration still TODO.
